## 0. 先搞清楚一堆 id：`NodeId`、`slot`、`port_id`、`Entity`

代码里有 4 套"身份"，很容易混。先摆清楚：

| 名字 | 类型 | 范围 | 含义 | 谁来起名 |
|---|---|---|---|---|
| `NodeId` | `int32_t` | 逻辑上任意（0..很大）| 一个拓扑节点的**逻辑 id**，比如"机器 42"、"交换机 101" | 用户输入（Python 里给的 nodes 列表） |
| `node_slot` | `int32_t` | `[0, numTopoNodes)` | `topoNodes[]` 数组里的**数组下标** | Sim 内部（按加载顺序分配） |
| `port_id` | `int32_t` | `[0, numPorts)` | 一条有向端口的**数组下标**（= 端口唯一编号） | Sim 内部 |
| `Entity` | `madrona::Entity` | ECS 句柄 | Madrona 给某个 Port archetype 实例的**ECS 句柄** | Madrona 引擎 |

> 关键区别：`NodeId` 是"外部名字"，`slot` 是"内部下标"。两者用 `findNodeSlot` 互相转换。

```cpp
struct TopoNodeState {
    NodeId id = -1;              // 外部名字
    NodeType type = NodeType::Host;
    Bw port_bw = 100.0;
    int32_t num_neighbors = 0;
    TopoNeighbor neighbors[MAX_NODE_NEIGHBORS] {};
};

struct TopoNeighbor {
    NodeId neighbor_id = -1;     // 邻居的 NodeId
    madrona::Entity port_entity; // 连向这个邻居的本地 Port 的 ECS 句柄
    int32_t port_id = -1;        // 连向这个邻居的本地 Port 的 port_id
};
```

**要点**：`TopoNeighbor.port_id` 就是"我（当前节点）出去连到 neighbor 的这条出端口的 port_id"，方向是**本节点 → 邻居**。`injectFlowDef` 就是靠这个字段把"NodeId 路径" 翻译成 "port_id 路径"。

## 1. 什么是"槽位"？为什么要 `findNodeSlot`

### 1.1 槽位 = 定长数组下标

`Sim` 里所有拓扑状态都存在定长数组里（为了 GPU 友好，不能用哈希表/`std::map`）：

```cpp
constexpr int32_t MAX_TOPO_NODES = 67;  // 容量
int32_t numTopoNodes;                   // 实际数量
TopoNodeState topoNodes[MAX_TOPO_NODES];
```

- `topoNodes[0] .. topoNodes[numTopoNodes-1]` 是当前 world 有效的节点。
- `topoNodes[i].id` 才是用户看到的 `NodeId`。
- `i` 就是 **slot**（"槽位"）。

> 举例：用户给了 3 个节点 `[NodeId=10, NodeId=42, NodeId=7]`，初始化后：
>
> | slot | topoNodes[slot].id | type |
> |---|---|---|
> | 0 | 10 | Host |
> | 1 | 42 | Switch |
> | 2 | 7 | Host |
>
> 用户说"节点 42"，代码需要知道"它住在 `topoNodes[1]`"，这一步就是 `findNodeSlot(42) → 1`。

### 1.2 为什么不直接用 `NodeId` 当下标？

因为 `NodeId` 是"稀疏的逻辑 id"：用户可能给 `{7, 42, 10000}` 这样三个节点，总共只有 3 个节点，但你若按 id 当下标就得开 10001 格数组——浪费且 MAX_TOPO_NODES 也开不到那么大。

所以做一层映射：

```cpp
int32_t Sim::findNodeSlot(NodeId node_id) const
{
    for (int32_t i = 0; i < numTopoNodes; i++) {
        if (topoNodes[i].id == node_id) return i;
    }
    return -1;  // 找不到
}
```

- **线性扫**，O(n)。n = `numTopoNodes`（小规模拓扑下很便宜，67 以内）。
- 找不到返回 `-1`，调用方要判。

### 1.3 邻居槽位 `findNeighborSlot`

类似：给定一个 node 的 slot，再在它的 `neighbors[]` 数组里线性找某个 `neighbor_id`，返回下标。

```cpp
int32_t Sim::findNeighborSlot(int32_t node_slot, NodeId neighbor_id) const
{
    const TopoNodeState &node = topoNodes[node_slot];
    for (int32_t i = 0; i < node.num_neighbors; i++) {
        if (node.neighbors[i].neighbor_id == neighbor_id) return i;
    }
    return -1;
}
```

找到之后就可以通过 `topoNodes[slot].neighbors[idx].port_id` 拿到**出端口号**。

## 2. 路由表：三张表是怎么一起工作的

`computeRoutes()`（`sim_world.cpp:54`）在初始化阶段跑一次，填好三张表。后续 `getPath` 只读。

### 2.1 三张表的含义

```cpp
NodeId routeTable[MAX_TOPO_NODES][MAX_TOPO_NODES];
int32_t ecmpCount[MAX_TOPO_NODES][MAX_TOPO_NODES];
NodeId ecmpNextHops[MAX_TOPO_NODES][MAX_TOPO_NODES][MAX_ECMP_NEXT_HOPS];
```

注意：**下标是 slot，不是 NodeId**。值是 NodeId。

| 表 | 含义 | 典型值 |
|---|---|---|
| `routeTable[src_slot][dst_slot]` | src→dst 的**单一**下一跳 NodeId（默认取 ECMP 第 0 个） | `-1`（不可达）或某个 NodeId |
| `ecmpCount[src_slot][dst_slot]` | 有多少个"等长"下一跳可选 | `0..MAX_ECMP_NEXT_HOPS (=8)` |
| `ecmpNextHops[src_slot][dst_slot][k]` | 第 k 个等长下一跳 NodeId | NodeId 或 `-1`（未填） |

### 2.2 怎么建表（两步）

**第 1 步：BFS 算全源最短距离**（只论跳数，不看带宽延迟）

```cpp
for (int32_t src_slot = 0; src_slot < numTopoNodes; src_slot++) {
    // 以 src_slot 为源，做 BFS
    // dist[src_slot][v_slot] = src 到 v 的最少跳数
}
```

产物：`dist[src_slot][dst_slot]`（代码里是局部二维数组，build 完就丢）。

**第 2 步：对每个 Switch 源，枚举每个目的，找所有"等长下一跳"**

```cpp
for (int32_t src_slot = 0; ...) {
    if (topoNodes[src_slot].type != NodeType::Switch) continue;  // 注意：只对 Switch 建
    for (int32_t dst_slot = 0; ...) {
        int32_t shortest = dist[src_slot][dst_slot];
        // 枚举 src 的每个直连邻居 neighbor
        // 若 1 + dist[neighbor][dst] == shortest，说明走 neighbor 正好是一条最短路径
        // 把 neighbor_id 塞进 ecmpNextHops[src_slot][dst_slot][count++]
    }
    ecmpCount[src_slot][dst_slot] = count;
    routeTable[src_slot][dst_slot] = ecmpNextHops[src_slot][dst_slot][0];  // 默认第 0 个
}
```

重要：**`routeTable` 只为 Switch 源建**。Host 源的那一行全是 `-1`。Host 的路由在 `getPath` 里单独处理（见下）。

### 2.3 为什么要 ECMP？

数据中心里两个 Switch 之间通常有多条等长路径（spine 层）。对同一 `(src, dst)`，不同 flow 散列到不同下一跳可以做负载均衡。

散列函数就是简单取模：

```cpp
inline int32_t hashFlowIndex(FlowId flow_id, int32_t count)
{
    return (int32_t)((uint64_t)flow_id % (uint64_t)count);
}
```

所以**同一个 flow 的每一跳都会稳定选到同一个 neighbor index 吗？**不完全——每一跳是 `hashFlowIndex(flow_id, ecmpCount[curr_slot][dst_slot])`，`curr_slot` 不同了模的基数也不同，结果也不同。这正好实现了"**每跳独立 ECMP**"。

### 2.4 查表使用：`getPath` 的核心两行

```cpp
int32_t ecmp_num = ecmpCount[curr_slot][dst_slot];
if (ecmp_num > 0) {
    int32_t idx = hashFlowIndex(flow_id, ecmp_num);
    curr = ecmpNextHops[curr_slot][dst_slot][idx];   // 走 ECMP
} else {
    NodeId next_hop = routeTable[curr_slot][dst_slot]; // 回退到单路
    if (next_hop < 0) return 0;                         // 不可达
    curr = next_hop;
}
```

## 3. getPath：用一个具体例子走一遍

### 3.1 函数签名与返回约定

```cpp
int32_t Sim::getPath(NodeId src,
                     NodeId dst,
                     FlowId flow_id,
                     NodeId *out_path,
                     int32_t max_path) const;
```

- **输入**：源/目的 `NodeId`，流 id（决定 ECMP 选哪条），`out_path` 是调用方准备好的缓冲区，`max_path` 是它的容量（通常是 `MAX_PATH_NODES = 16`）。
- **输出**：返回值是实际写入的长度 `count`。`out_path[0..count-1]` 是 NodeId 序列，满足 `out_path[0] == src` 且 `out_path[count-1] == dst`。
- **失败**：返回 0（下标越界/拓扑断链/容量不够等等）。

### 3.2 例子拓扑

```
        [Sw 42]
        /      \
       /        \
  [ToR 10]    [ToR 20]
     |           |
  [H 7]       [H 8]
```

- Host 7 的 NodeId = 7，只有一个邻居 ToR 10。
- Host 8 的 NodeId = 8，只有一个邻居 ToR 20。
- ToR 10、ToR 20 都只通 Sw 42。
- Sw 42 为了简单，只有这两条下行邻居。

slot 映射（假设按加载顺序）：

| NodeId | slot | type |
|---|---|---|
| 7 | 0 | Host |
| 10 | 1 | Switch |
| 20 | 2 | Switch |
| 42 | 3 | Switch |
| 8 | 4 | Host |

`computeRoutes` 算完之后（简化起见，每个对只有 1 条最短路径，ECMP count 都是 1）：

- `routeTable[1][4] = 42`（ToR10 到 H8 要去 Sw42）
- `routeTable[3][4] = 20`（Sw42 到 H8 要去 ToR20）
- `routeTable[2][4] = 8` （ToR20 直接到 H8）
- Host 的行（slot 0、4）全是 -1。

### 3.3 一步步走 `getPath(src=7, dst=8, flow_id=...)`

初始：`count=0`, `curr=7`, `out_path[0]=7 → count=1`。

**第 1 跳**：`curr=7`（Host）
- `findNodeSlot(7) = 0`，`topoNodes[0].type = Host`。
- 进 Host 分支：先 `findNeighborSlot(0, dst=8)` —— 7 的邻居只有 10，找不到 8，返回 -1。
- 退回去走 `neighbors[0].neighbor_id = 10`。
- `curr = 10`, `out_path[1]=10 → count=2`。

**第 2 跳**：`curr=10`（Switch）
- `findNodeSlot(10) = 1`。
- `findNodeSlot(dst=8) = 4`。
- `ecmpCount[1][4] = 1`，`idx = flow_id % 1 = 0`，`curr = ecmpNextHops[1][4][0] = 42`。
- `out_path[2]=42 → count=3`。

**第 3 跳**：`curr=42`（Switch）
- `slot=3`，`dst_slot=4`。
- `ecmpCount[3][4] = 1`，`curr = ecmpNextHops[3][4][0] = 20`。
- `out_path[3]=20 → count=4`。

**第 4 跳**：`curr=20`（Switch）
- `slot=2`，`dst_slot=4`。
- `ecmpCount[2][4] = 1`，`curr = 8`。
- `out_path[4]=8 → count=5`。

**循环结束**（`curr == dst`）。`out_path[count-1] == dst`，返回 `count=5`。

**最终 `out_path`**：`[7, 10, 42, 20, 8]`，长度 5。这就是一串 **NodeId 序列**，还不是 port 序列。

### 3.4 Host 分支的两种情况

`getPath` 里 Host 分支的代码：

```cpp
if (node.type == NodeType::Host) {
    if (node.num_neighbors <= 0) return 0;

    // 情况 A：dst 正好是我的直连邻居（Host 直连 Host，罕见但支持）
    int32_t direct_idx = findNeighborSlot(curr_slot, dst);
    if (direct_idx >= 0) {
        curr = dst; out_path[count++] = curr; break;
    }

    // 情况 B：走第 0 个邻居（一般是唯一的 ToR）
    curr = node.neighbors[0].neighbor_id;
    out_path[count++] = curr;
    continue;
}
```

Host 不走 `routeTable`（因为 `routeTable` 只对 Switch 源建）。通常 Host 只有一个 ToR 邻居，所以直接把包扔给 ToR 就行，剩下的交给 Switch 层路由。

### 3.5 失败场景

| 场景 | 返回 |
|---|---|
| `max_path <= 0` | 0 |
| 途中 `findNodeSlot(curr)` 返回 -1（节点不存在）| 0 |
| Host 没邻居 | 0 |
| Switch 的 `ecmpCount == 0` 且 `routeTable[..] < 0`（不可达）| 0 |
| 循环写了 `max_path` 步还没到 dst（跳数太多，防死循环）| 0（末尾不等于 dst）|

## 4. `injectFlowDef` vs `injectFlow`：两个函数的分工

现在回到你最困惑的点。它俩名字很像，只差一个 `Def`，实际**分层明确**：

### 4.1 一句话区别

- `injectFlowDef(flow)`：**流定义级**。只知道"这条 flow 的 src_node / dst_node"，需要**算路径、登记路由**，然后再把"起点端口"算出来，喊 `injectFlow`。
- `injectFlow(src_port_id, flow)`：**端口级**。已经知道"这条 flow 从哪个 port 开始注入"，只负责**构造一个 Arrival 延迟事件并入堆**。

可以理解为：`injectFlowDef` 是"**配送调度员**"（派件员，算地址），`injectFlow` 是"**派送工**"（到点投递）。

### 4.2 `injectFlowDef` 做的 4 件事

```cpp
void Sim::injectFlowDef(const FlowDef &flow) {
    // 1) 算 NodeId 路径
    NodeId path[MAX_PATH_NODES] {};
    int32_t path_len = getPath(flow.src_node, flow.dst_node, flow.id,
                               path, MAX_PATH_NODES);
    if (path_len < 2) return;

    // 2) 把 NodeId 路径翻译成 port_id 路径
    int32_t port_path[MAX_FLOW_ROUTE_STEPS + 1] {};
    int32_t port_path_len = 0;
    for (int32_t i = 0; i + 1 < path_len; i++) {
        int32_t node_slot = findNodeSlot(path[i]);
        int32_t neighbor_idx = findNeighborSlot(node_slot, path[i + 1]);
        port_path[port_path_len++] = topoNodes[node_slot].neighbors[neighbor_idx].port_id;
    }
    port_path[port_path_len++] = -1;   // 末尾 -1 哨兵

    // 3) 登记到 flowRoutes（幂等）
    if (!exists && numFlowRoutes < MAX_FLOWS) {
        FlowRouteState &route = flowRoutes[numFlowRoutes++];
        route.flow_id = flow.id;
        route.num_steps = port_path_len - 1;
        for (int32_t i = 0; i + 1 < port_path_len; i++) {
            route.steps[i] = { port_path[i], port_path[i + 1] };
        }
    }

    // 4) 找到起点 port_id，转交给 injectFlow
    int32_t src_port_id = topoNodes[src_slot].neighbors[first_neighbor_idx].port_id;
    injectFlow(src_port_id, flow);
}
```

继续用第 3 节的例子：`path = [7, 10, 42, 20, 8]`，翻译成 port_id 序列：

| i | path[i] → path[i+1] | slot(path[i]) | 这条边的出端口 `port_id`（举例编号）|
|---|---|---|---|
| 0 | 7 → 10 | 0 | P(7→10) = 101 |
| 1 | 10 → 42 | 1 | P(10→42) = 102 |
| 2 | 42 → 20 | 3 | P(42→20) = 103 |
| 3 | 20 → 8 | 2 | P(20→8) = 104 |

→ `port_path = [101, 102, 103, 104, -1]`，`port_path_len = 5`。

登记到 `flowRoutes`：

```
flowRoutes[k] = {
  flow_id = flow.id,
  num_steps = 4,
  steps = [
    { port_id=101, next_port_id=102 },
    { port_id=102, next_port_id=103 },
    { port_id=103, next_port_id=104 },
    { port_id=104, next_port_id=-1 }   // -1 表示"最后一跳，没有下一跳"
  ]
}
```

> `-1` 哨兵是"下一跳端口"占位。下游系统（例如 `lookupFlowRouteNext`）查到 `next_port_id == -1` 就知道包要"上岸"（到达目的 Host）。

最后一步：`src_port_id = 101`（第一跳 7→10 的那个 port），调用 `injectFlow(101, flow)`。

### 4.3 `injectFlow` 做的 3 件事

```cpp
void Sim::injectFlow(int32_t src_port_id, const FlowDef &flow) {
    // 1) 算 src 端口的输入带宽（取 link bandwidth，否则用 node.port_bw）
    Bw src_in_bw = 0.0;
    if (src_port_id valid) {
        ... src_in_bw = topoLinks[src_port_id].bandwidth > 0 ? ... : node.port_bw;
    }

    // 2) 拼一个 t=now 的 Arrival 延迟事件
    DelayedEvent ev {};
    ev.t = now;
    ev.type = DelayedEvent::Type::Arrival;
    ev.arrival = FlowArrivalEv {
        .port_id = src_port_id,
        .flow_id = flow.id,
        .size = flow.size,
        .in_bw = src_in_bw,
        .is_source = 1,              // 关键：表示这是"源头"进入点
        .priority = flow.priority,
    };

    // 3) 入堆
    pushDelayedEvent(ev);
}
```

它**什么路径都不算**——因为它的调用者已经把 `src_port_id` 塞给它了。

### 4.4 为什么要拆成两个函数？

因为"注入一条流到某个端口"这件事**有两个来源**：

1. **`schedulePendingFlows` 场景**：从 `pendingFlows` 里弹出一条 `FlowDef`，只有逻辑节点 id，要先算路径 → 用 `injectFlowDef`。
2. **其他场景**：已经知道 src_port（比如某个 bind 好的接入点），直接 `injectFlow`。
   > 当前仓库里 `injectFlow` 只被 `injectFlowDef` 调用；但这个分层给将来"在某个端口强行注入流"留了口子。

## 5. 串起来：从 `schedulePendingFlows` 开始的完整调用链

把例子再拉通一次。假设 `now = 1.0s`，`pendingFlows[0] = FlowDef{ id=99, src_node=7, dst_node=8, size=1MB, start_time=1.0, priority=0 }`。

```
schedulePendingFlows()
  while (pendingFlows[0].start_time <= 1.0 + 1e-15):
    flow = pendingFlows[0]       # {id=99, 7→8, 1MB, 1.0, ...}
    pendingFlows 左移 1 格
    numPendingFlows -= 1         # 流从待排队列出队
    injectFlowDef(flow)
    │
    ├── getPath(7, 8, 99, out_path, 16)
    │     return 5, out_path = [7, 10, 42, 20, 8]
    │
    ├── 翻译成 port_path = [101, 102, 103, 104, -1]
    │
    ├── 新增 flowRoutes[k] = { flow_id=99, num_steps=4, steps=[...] }
    │   (若 flow_id=99 已存在则跳过)
    │
    └── injectFlow(src_port_id=101, flow)
          │
          ├── 算 src_in_bw（根据 topoLinks[101] 或 node.port_bw）
          │
          ├── ev = DelayedEvent {
          │       t = 1.0,
          │       type = Arrival,
          │       arrival = { port_id=101, flow_id=99, size=1MB,
          │                   in_bw=..., is_source=1, priority=0 }
          │     }
          │
          └── pushDelayedEvent(ev)
                └── delayedEvents[numDelayedEvents++] = ev
                    保持按 t 升序（反向冒泡一次）
```

执行后**状态变化**：

| 数组 | 之前 | 之后 |
|---|---|---|
| `pendingFlows[]` / `numPendingFlows` | 含 flow 99 | 不含 |
| `flowRoutes[]` / `numFlowRoutes` | 不含 99 | +1 条（num_steps=4）|
| `delayedEvents[]` / `numDelayedEvents` | - | +1 条 `t=1.0` 的 Arrival |
| 任何 ECS Entity / Component | - | **不变** |

Entity 级的创建（`FlowTag`、`DirtyPort=1` 等）要等到下一阶段 `deliverEvents` + `flowArrivalSystem` 消费这个 `DelayedEvent` 时才会发生。

## 6. 常见困惑 FAQ

**Q1：`port_path` 最后那个 `-1` 为什么要加？**
A：把 `port_path` 当成"每跳的出端口"数组，长度和 NodeId 路径的边数相同。但 `FlowRouteState.steps[i]` 要同时存 `{port_id, next_port_id}`——对最后一跳来说"next_port_id"不存在，用 `-1` 哨兵填。这样下游 `lookupFlowRouteNext(flow_id, 104)` 返回 -1 就知道是终点。

**Q2：`getPath` 返回的是 Node 还是 port？**
A：是 **NodeId 序列**。把它翻译成 `port_id` 序列是 `injectFlowDef` 自己的工作。

**Q3：ECMP 是"每跳独立散列"还是"整条路径一次选定"？**
A：**每跳独立散列**。每跳 `hashFlowIndex(flow_id, ecmpCount[curr_slot][dst_slot])`，基数不同，选法不同。同一 flow 在同一拓扑下是确定性的（只要 `flow_id` 不变），但不同 `(curr_slot, dst_slot)` 的选择互相独立。

**Q4：Host 节点不在 `routeTable` 里，那 Host → Host 怎么办？**
A：Host 分支在 `getPath` 里单独写死：先看 dst 是不是我直连邻居，不是就把包扔给第一个邻居（通常是唯一的 ToR），从 ToR 开始就走 Switch 的 `routeTable / ecmpNextHops` 了。

**Q5：`numFlowRoutes` 到了上限还会调 `injectFlow` 吗？**
A：会。只会跳过路由登记，事件照常入堆。但后续系统若靠 `lookupFlowRouteNext` 找下一跳，就查不到而失败——这是一个已知边界。

**Q6：`findNodeSlot` 线性扫不慢吗？**
A：当前 `MAX_TOPO_NODES = 67`，线性扫每次最多 67 次比较，GPU 上也非常便宜；切到大规模（注释里 1152 节点）时仍然 O(n)，可接受但会是热点，日后可能换成哈希或在 init 时建一张 `NodeId → slot` 的映射表。
