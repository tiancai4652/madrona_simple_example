# 流仿真器业务逻辑讲解（按代码真实流程）

> 目标：不讲框架，只讲这个“流仿真器”本身怎么初始化、怎么跑、每个系统做什么、实体什么时候创建。

## 1. 先用一句话理解这个模型

这个仿真器把“网络里的一个流”拆成一串沿路径前进的 `FlowTag`。
每个 `FlowTag` 挂在某个端口（Port）上，记录这个流在该端口的输入带宽、输出带宽、积压（backlog）、剩余量（source 端）。

每一帧会做三件大事：
1. 先把“到时的事件”投递到端口（到达、带宽变化、PFC控制）。
2. 再按端口算当前应该发多少（分配带宽、是否触发PFC、是否给下游发新事件）。
3. 最后推进时间 `now += dt`，处理计时器和完成清理。

---

## 2. 初始化到底做了什么

初始化入口在 `Sim::Sim(...)`，顺序非常关键：

1. `resetNetworkState()`
- 清空仿真时钟 `now`、各种计数器、定时器、缓存。
- 清空拓扑数组、路由表、事件队列、Tag索引、完成记录。
- 设置默认参数（buffer/pfc开关、默认链路时延、阈值等）。

2. 读取配置覆盖默认值
- `enableBuffer`、`enablePfc`、`pfcEgress`、`defaultLinkDelay`、`propagationInterval`、`dtMin`、`qosMode`、`priorWeights` 等。

3. 创建两个“常驻实体”
- `Agent`：兼容原 grid 示例的导出字段（Reset/Action/Reward...）。
- `SimDriverArch`：驱动全局系统用的单实体（tick 计数等）。

4. `loadTopo(ctx)` 加载拓扑
- 读取 `network->nodes` 和 `network->links`。
- 每条输入链路会转成双向链路。
- 为每个“节点到邻居”的方向创建一个 `Port` 实体（`createPort`）。
- 建立 `peerPort`（反向对应端口）和 `connected` 标记。
- 计算路由/ECMP（`computeRoutes`）。

5. `loadFlow(ctx)` 加载流定义
- 复制 `network->flows` 到 `flowDefs` 与 `pendingFlows`。
- `pendingFlows` 按 `start_time` 升序排序，后续按时间注入。

---

## 3. 实体什么时候创建 / 销毁

## 3.1 会创建哪些实体

1. `Agent`
- 创建时机：构造函数里初始化阶段。
- 数量：1。

2. `SimDriverArch`
- 创建时机：构造函数里初始化阶段。
- 数量：1。

3. `Port`
- 创建时机：`loadTopo -> createPort`。
- 每个方向一条链路一个端口，所以是“有向端口”。

4. `FlowTag`
- 创建时机不是初始化，而是运行时：
  - 处理到达事件 `Arrival` 时，若该端口该流还没有 tag，会创建。
  - 处理带宽更新 `BwUpdate(in_bw>0)` 时，若没有 tag，也会创建。
- 真正创建动作在 `flushTagCreate()` 里统一执行（为了顺序稳定）。

## 3.2 什么时候销毁 `FlowTag`

会在这些场景销毁：
1. 上游给了 `in_bw=0`，且没有 backlog 可排空（或策略判定应清理）。
2. 缓冲推进阶段发现 backlog 清空、上游也不再存活。
3. 源端 `remaining` 发完后，完成回收。

销毁通过 `destroyTag()`，同时会：
- 从 `tagIndex / PortTagList / ingressTags / sourceTags` 移除。
- 必要时记录流完成 `recordFlowCompletion()`。
- 必要时向下游发 cleanup 事件（`BwUpdate=0`）。

## 4. 每一帧系统流转（主流程）

代码里的任务图是一条固定流水线，可以理解成下面 8 段：

1. `scheduleStepSystem`
- `tick++`
- `schedulePendingFlows()`：把到启动时间的流注入为首个 `Arrival` 事件。

2. `deliverStepSystem`
- `deliverEvents()`：把 `delayedEvents` 中到时事件分发到每个端口的 `PortInbox`。

3. Ingress 链（按端口并行）
- `pfcPropagateOnePort`：应用收到的 PFC pause/resume。
- `flowArrivalOnePort`：处理 Arrival（更新已有tag或登记待创建）。
- `flushTagCreate`：真正创建本轮新tag。
- `bwUpdateOnePort`：处理 BwUpdate（更新、清理、转发、完成登记）。
- `flushTagCreate`（第二次）：让 bwupdate 里登记的新建也落地。
- `flushTagCleanup`：执行延期销毁。
- `flushFlowCompletion`：写入完成记录。
- `flushPortOutbox`：把端口 outbox 事件并回全局延迟队列。
- `logIngressChain`：汇总日志。

4. `allocOnePort`（按端口并行）
- 根据 QoS/SP/WRR、PFC状态、buffer/backlog 给每个 tag 分配 `out_bw`。
- 产出“下一次可能事件”的 hint（最快 drain/finish 时间）。

5. alloc 后单例归并
- `reducePortCachedHints`、`flushPortDrainHints`、`flushTagCleanup`、`logAllocTraces`。

6. 发包/PFC 检测链
- `pfcDetectOnePort`：检查阈值，决定是否发 PFC 控制事件。
- `flushPfcTimers` + `flushPortOutbox` + `logPfcDetectTraces`。
- `emitOnePort`：对下游发 Arrival/BwUpdate。
- `flushPortOutbox` + `logEmitTraces`。

7. 脏端口快照与步长
- `clearDirtyOnePort`：清 dirty 并记快照。
- `snapshotDirtyPorts`：重建“上一帧哪些端口是脏的”。
- `chooseDT`：计算下一小步时间 `dt`。

8. buffer 推进与时间前进
- `advanceOnePortBuffer(dt)`：推进 backlog/buffer/chunk。
- `flushBufferTagCleanup` + `logBufferTraces`。
- `flowProgressAndCleanupSystem(dt)`：处理源流完成、计时器到期、最终 `now += dt`。

## 5. 每个系统具体做什么（通俗版）

## 5.1 schedule_pending_flows

作用：把“该开始的流”放进系统。

做法：
- 从 `pendingFlows` 头部不断弹出 `start_time <= now` 的流。
- 通过路由算首跳端口，塞一条 `Arrival` 事件（时间就是 now）。

结果：流还没变成 tag，只是“预约了一条到达事件”。

## 5.2 deliver_events

作用：把到时事件投递到对应端口邮箱。

做法：
- 扫 `delayedEvents`，把 `t <= now` 的事件取出。
- 按类型放进 `PortInbox.arrivals / bwupds / pfcs`。
- 未到时事件保留在 `delayedEvents`。

结果：后续端口并行系统只看自己的 inbox，不扫全局队列。

## 5.3 pfc_propagate（端口收控制）

作用：端口收到 pause/resume 控制后，更新本端口优先级暂停状态。

结果：被 pause 的优先级在分配带宽阶段会被压成 0 或受限。

## 5.4 flow_arrival

作用：处理“某流到达某端口”。

做法：
- 如果已有 tag：更新 `in_bw`，源端可刷新 `remaining`。
- 没有 tag：先登记到 `PortCreateList`，由 `flushTagCreate` 统一创建。

## 5.5 bw_update_ingress

作用：处理“某端口某流带宽变化”。

关键分支：
1. `in_bw == 0`
- 有 backlog 且开 buffer：设 `in_bw=0`，继续排空（不立刻删）。
- 无 backlog：销毁 tag，并可能向下游转 cleanup。

2. `in_bw > 0`
- 无 tag：创建（或若同批有cleanup信号则向下游透传cleanup/完成）。
- 有 tag：更新 `in_bw`。

## 5.6 alloc（带宽分配）

作用：给每个端口上的每个活跃 tag 算 `out_bw`。

考虑因素：
- 端口总带宽 `port_bw`
- QoS 模式（无QoS / SP / WRR）
- PFC pause 状态
- 该优先级是否有 backlog chunk

同时会输出两个“下一事件预测”：
- `finish_hint`：最早哪个源流会发完。
- `drain_hint`：最早哪个积压会被排空。

## 5.7 pfc_detect（端口发控制）

作用：看 backlog 是否过 XOFF/XON，决定要不要给上游发 pause/resume。

两种模式：
- `pfcEgress=1`：按 egress 端口检测。
- `pfcEgress=0`：按 ingress 端口检测。

输出：
- 控制事件写入 `PortOutbox`（后续统一 flush）。
- pause/resume timer 变更先写 `want_*`，再统一 flush。

## 5.8 emit（下游发包）

作用：把本端口 tag 的输出带宽传播给下游端口。

规则：
- 首次下游创建：发 `Arrival`（并标记 `downstream_created=1`）。
- 后续变化：仅当 `out_bw != prev_out_bw` 才发 `BwUpdate`。

## 5.9 clear_dirty + choose_dt + buffer + progress

1. `clear_dirty/snapshot`
- 清理 dirty 标记，但保留“本帧哪些端口曾脏”的快照，供下阶段判断。

2. `chooseDT`
- 从这些最小值里选下个 `dt`：
  - 下一条延迟事件到达时间
  - 下一条待启动流时间
  - 下一次源流完成预测
  - 下一次drain预测
  - backlog/pfc pause/pfc resume 定时器
- 再应用 `dtMin` 下限；异常时退回 `0.001`。

3. `advanceOnePortBuffer(dt)`
- 推进 buffer 数量和 chunk。
- 回写 tag backlog。
- 必要时把可清理 tag 放入 cleanup 列表。

4. `flowProgressAndCleanupSystem(dt)`
- 源流 `remaining` 递减，完成则发 cleanup 并销毁。
- 所有计时器递减，到期触发端口重新变脏。
- 最后 `now += dt`。

---

## 6. 一个流从开始到结束（故事版）

1. 到了 `start_time`，被 `schedule_pending_flows` 注入首个 Arrival。
2. `deliver_events` 把 Arrival 投给首跳端口。
3. `flow_arrival + flushTagCreate` 生成源 tag。
4. `alloc` 给它算 `out_bw`。
5. `emit` 给下一跳发 Arrival（第一次）或 BwUpdate（后续变化）。
6. 下游端口重复 3~5，沿路由推进。
7. 若拥塞，backlog 变大，可能触发 `pfc_detect` 发 pause；缓解后发 resume。
8. 源端 `remaining` 清零后，进入 cleanup 链，沿路由清掉下游残留 tag。
9. 最终 `recordFlowCompletion` 写完成记录（FCT = end_time - start_time）。

---

## 7. 你讲给别人时可以用的三句话

1. 这是个“事件驱动 + 小步长推进”的端口级流仿真器。
2. 流不是整条一起算，而是拆成每跳的 `FlowTag`，在端口间靠 Arrival/BwUpdate 事件传播。
3. 拥塞靠 backlog 表示，带宽分配决定 out_bw，PFC 用阈值触发 pause/resume 控制上游。
