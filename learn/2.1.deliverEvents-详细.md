# 2.1 deliverEvents 深入版：事件类型、端口 Inbox、双写与压缩

这篇是 `2.deliverEvents.md` 的补充。只回答 5 个具体问题：

1. 本函数涉及的 **ECS 实体和 Component** 到底是什么？为什么有 `portEntities[port_id]` 这一层？
2. **三类延迟事件**（`Arrival / BwUpdate / PfcControl`）分别从哪儿来、什么语义？为什么 PFC 要用 `target_port_id` 而不是 `port_id`？
3. 为什么要做"**双写**"（全局 inbox + per-Port inbox）？为什么不直接写一份？
4. `delayedEvents[]` 的**双指针压缩**具体是怎么工作的？
5. `PortCreateList / PortCompletionList` **只清零不追加**，那它们是干嘛用的？谁来填？

读完之后应该能完整回答：**一个 `DelayedEvent` 从"入堆"到"被某个 per-Port 系统真正消费"**中间经过了哪些数据结构。

---

## 0. ECS 速览：先把 Entity / Component / Archetype 铺平

`deliverEvents` 是整个仓库里**第一处大量 `ctx.get<X>(entity)`** 的函数，所以先把 Madrona 的 ECS 概念说一下。

- **Entity**：`madrona::Entity`，是一个轻量句柄（可以理解为一个 id），指向 ECS 里的一条"记录"。
- **Component**：一个 POD 结构体，挂在某个 Entity 上。比如 `PortState / PortInbox / DirtyPort` 都是 Component。
- **Archetype**：Entity 的"类型"，就是"这种 Entity 拥有哪些 Component 的集合"。`Port` archetype 定义了 14 个 Component：

```cpp
struct Port : public madrona::Archetype<
    DirtyPort, PortState, PortBuffer, PortPfcConfig, PortPfcState,
    PortCachedHints, PortDrainHint, PortCleanup, PortTraceLast,
    PortOutbox, PortTagList, PortInbox, PortCreateList, PortCompletionList
> {};
```

- 取 Component：`ctx.get<PortInbox>(port_entity)` 返回对**那个 Entity 的 PortInbox 字段**的引用，可读可写。
- 创建 Entity：`ctx.makeEntity<Port>()`（本函数**不**创建）。

### 0.1 `portEntities[]` 是什么

```cpp
Entity portEntities[MAX_TOPO_PORTS];   // port_id → Entity
int32_t numPorts;
```

`port_id` 是"端口的紧凑整数编号"，ECS 的 Entity 是不透明句柄。需要靠一张索引表把数字 id 翻译成 ECS 句柄，`portEntities[]` 就是这张表。

> 为什么要这层间接？因为在 `DelayedEvent` 里只能存 `port_id`（一个 int），不能存 Entity（Entity 可能在不同 world 里值不同，不适合当事件载荷）。所以事件里用 `port_id`，真要访问 Component 时再 `portEntities[port_id]` 取回 Entity。

### 0.2 本函数真正"动"的 3 个 Component

`deliverEvents` 在整个 `Port` archetype 的 14 个 Component 里，**只碰** 3 个：

| Component | 作用 | 本函数对它做了啥 |
|---|---|---|
| `PortInbox` | 本步要消费的到期事件缓冲（3 类） | `num_* = 0` 清零，然后按类型追加 |
| `PortCreateList` | 下游延迟创建 Tag 的请求队列 | 只 `num = 0` 清零；不追加 |
| `PortCompletionList` | 下游延迟登记流完成的请求队列 | 只 `num = 0` 清零；不追加 |

其他 11 个 Component（`PortState / PortBuffer / DirtyPort / ...`）本函数**一行都不碰**，全部留给后续 per-Port 系统。

## 1. 三类延迟事件：语义、生产者、消费者

`DelayedEvent` 是个 tagged union，`type` 字段决定哪一份子载荷有效：

```cpp
struct DelayedEvent {
    enum class Type : int32_t { Arrival, BwUpdate, PfcControl } type;
    Time t;                  // 到期时间
    FlowArrivalEv arrival;   // type == Arrival 时有效
    BwUpdateEv bwupd;        // type == BwUpdate 时有效
    PfcControlEv pfcctrl;    // type == PfcControl 时有效
};
```

### 1.1 `FlowArrivalEv`：新 flow 抵达某端口

```cpp
struct FlowArrivalEv {
    int32_t port_id = -1;   // 这个 flow 到达的端口
    FlowId flow_id = -1;
    Bytes size = 0.0;       // 剩余要传输的 bytes
    Bw in_bw = 0.0;         // 入端带宽估值
    int32_t is_source = 0;  // 1: 是源头；0: 是中间 hop
    int32_t priority = 0;
};
```

**谁生产**：
- `injectFlow()`：源头注入（`is_source = 1`）。来自 `schedulePendingFlows → injectFlowDef`。
- `PortOutbox → flushPortOutbox`：端口转发时，下一跳端口会收到一条 Arrival（`is_source = 0`）。
- 清理逻辑里也会塞一些（详见 `sim_systems_pfc.cpp` 等）。

**消费者**：per-Port 系统 `flowArrivalOnePort`（sim_systems.cpp:567 附近）。它会把这些事件翻译成"在 Port 上创建/更新 FlowTag"的操作。

### 1.2 `BwUpdateEv`：某端口上某 flow 的入端带宽变了

```cpp
struct BwUpdateEv {
    int32_t port_id = -1;
    FlowId flow_id = -1;
    Bw in_bw = 0.0;
};
```

**谁生产**：上游端口在 `bwUpdate` 系统里算出"我给下游送这个 flow 的出速率变了"，把新速率包成 BwUpdateEv 入堆，用 link delay 延迟送达下游。

**消费者**：下游端口的 `bwUpdateOnePort` 系统——它根据新 `in_bw` 重算 FlowTag 的 `out_bw`，并递归产生下下游的 BwUpdateEv。

### 1.3 `PfcControlEv`：上游告诉下游"你给我 PAUSE / RESUME"

```cpp
struct PfcControlEv {
    int32_t target_port_id = -1;  // 谁收到这条控制（被暂停/恢复的对象）
    int32_t source_port_id = -1;  // 谁发起的（通常是检测到拥塞的那个端口）
    int32_t priority = 0;         // 哪个优先级被 PAUSE
    int32_t paused = 0;           // 1: PAUSE；0: RESUME
};
```

**方向感**：PFC 是"**反向信令**"。例子：端口 B 的下游拥塞了 → B 往**上游** A 发一个 PfcControlEv，`source_port_id = B`，`target_port_id = A`。A 收到后停止往 B 发这个优先级的包。

这就是为什么 `deliverEvents` 里 PfcControl 要用 `target_port_id` 作路由键：

```cpp
// Arrival / BwUpdate：事件发生在 port_id 这个端口上
if (ev.port_id >= 0 && ev.port_id < numPorts) { ... }

// PfcControl：事件的"收件人"是 target_port_id
if (ev.target_port_id >= 0 && ev.target_port_id < numPorts) { ... }
```

**谁生产**：`pfcDetect / pfcPropagate` 系统。
**消费者**：`pfcPropagateOnePort`——读自己的 `PortInbox.pfcs[]`，更新 `PortPfcState`。

### 1.4 三类事件共用一张 `delayedEvents[]` 的好处

只有一张按 `t` 排序的数组，所有时间调度一致：

- `chooseDT()` 只需要看 `delayedEvents[0].t`（最早到期时间）就能算下一步的 dt。
- 所有时间触发的后果（新 flow 到达、带宽改变、PFC 触发）都在同一时间轴上，不会错序。

而分发到 per-Port 时再按类型分开存，是为了让每个 Port 的 worker 只处理**自己这个端口相关的**那一小撮事件。

## 2. 为什么要"双写"：全局 inbox + per-Port inbox

### 2.1 两套 inbox 同时存在

```cpp
// Sim 单例上的"全局 inbox"（每类一个大数组）
int32_t numInboxArrival;
FlowArrivalEv inboxArrival[MAX_EVENTS_PER_STEP];  // 容量 16384
int32_t numInboxBwUpdate;
BwUpdateEv inboxBwUpdate[MAX_EVENTS_PER_STEP];
int32_t numInboxPfc;
PfcControlEv inboxPfc[MAX_EVENTS_PER_STEP];

// 每个 Port Entity 上的 PortInbox Component
struct PortInbox {
    int32_t num_arrival;
    FlowArrivalEv arrivals[MAX_PORT_INBOX_ARRIVAL];  // 容量 64
    int32_t num_bwupd;
    BwUpdateEv bwupds[MAX_PORT_INBOX_BWUPD];         // 容量 64
    int32_t num_pfc;
    PfcControlEv pfcs[MAX_PORT_INBOX_PFC];           // 容量 32
};
```

`deliverEvents` 每派发一个事件，**同时**往这两个地方写一份：

```cpp
// 全局
if (numInboxArrival < MAX_EVENTS_PER_STEP) {
    inboxArrival[numInboxArrival++] = ev;
}
// per-Port
PortInbox &inbox = ctx.get<PortInbox>(port_e);
if (inbox.num_arrival < MAX_PORT_INBOX_ARRIVAL) {
    inbox.arrivals[inbox.num_arrival++] = ev;
}
```

### 2.2 为什么要留一份全局？

这是历史 + 并存设计：

- 老路径（`flowArrivalSystem / bwUpdateSystem / ...`，Phase E 之前的写法）是 Sim 单例里串行扫全局 `inboxArrival[]` 全部处理。
- 新路径（Phase E）是 per-Port 并行，每个 Port 的 worker 只读自己的 `PortInbox`。
- 两套路径目前**并存**（你能在 `sim_systems.cpp` 看到 `flowArrivalSystem` 仍然在扫 `inboxArrival`；也看得到 `flowArrivalOnePort` 扫 `inbox.arrivals`）。为了让两套看到同一份事件，`deliverEvents` 就双写。
- 日志也需要全局视角（一步到底派发了多少事件，不关心分到哪个 Port），所以 `printSystemDeliverArrival` 是在全局分支里打的。

### 2.3 容量差距造成的"信息不对称"

| 容量 | Arrival | BwUpdate | PfcControl |
|---|---|---|---|
| 全局 `MAX_EVENTS_PER_STEP` | 16384 | 16384 | 16384 |
| 每 Port `MAX_PORT_INBOX_*` | 64 | 64 | 32 |

全局容量远大于单 Port 容量。**两边独立判容量，各自溢出静默丢**：

- 一个事件可能只写进全局，没写进 per-Port（per-Port 满了）→ Phase E per-Port worker 看不到。
- 也可能只写进 per-Port，没写进全局（全局满了，罕见）→ 老路径 + 日志看不到。

对调试的影响：**如果你看到 per-Port 有事件但全局日志没打**，或反过来，原因就是某一侧容量溢出。

### 2.4 端口级分流的并行优势

所有 Arrival 先进一个大数组，每个 Port 的 worker 要找"我的事件"还得线性扫全局数组。分流到 `PortInbox` 之后，每个 worker 只看自家那 64 条，扫描代价从"O(全局事件数)"降到"O(本 Port 事件数)"，并行时互不干扰——这是分流的根本动机。

## 3. 双指针压缩：一个具体例子

主循环：

```cpp
int32_t write_idx = 0;
for (int32_t i = 0; i < numDelayedEvents; i++) {
    if (delayedEvents[i].t <= now + 1e-15) {
        /* 到期：分发到 inbox，不写回 delayedEvents */
    } else {
        delayedEvents[write_idx++] = delayedEvents[i];  // 未到期：搬到前面
    }
}
numDelayedEvents = write_idx;
```

### 3.1 例子：5 个事件，now = 1.0s

假设 `delayedEvents[]` 当前有 5 条：

| i | t | 说明 | 判到期（t ≤ 1.0）|
|---|---|---|---|
| 0 | 0.9 | Arrival | 是 |
| 1 | 1.0 | BwUpdate | 是（含 1e-15 容差）|
| 2 | 1.2 | Pfc | 否 |
| 3 | 1.5 | Arrival | 否 |
| 4 | 2.0 | Arrival | 否 |

`pushDelayedEvent` 维护了近似升序，所以这是典型排布。

逐步：

- `i=0, t=0.9` → 到期 → 分发到全局/per-Port inbox；`write_idx` 不动。
- `i=1, t=1.0` → 到期 → 分发；`write_idx` 不动。
- `i=2, t=1.2` → 未到期 → `delayedEvents[0] = delayedEvents[2]`，`write_idx=1`。
- `i=3, t=1.5` → 未到期 → `delayedEvents[1] = delayedEvents[3]`，`write_idx=2`。
- `i=4, t=2.0` → 未到期 → `delayedEvents[2] = delayedEvents[4]`，`write_idx=3`。

循环结束：`numDelayedEvents = 3`，`delayedEvents[0..2] = [{t=1.2}, {t=1.5}, {t=2.0}]`。

### 3.2 几个细节

- **就地压缩**：只要 `write_idx <= i` 永远成立，写不会覆盖还没读到的元素。这里 `write_idx <= i` 自证：任何时候 `write_idx + 已到期数 = i + 1`，所以 `write_idx <= i + 1`，且下一次循环 `i` 会先 +1 再读，所以安全。
- **不清尾部**：`numDelayedEvents = 3` 之后，`delayedEvents[3..4]` 的内容还是老数据，但被逻辑视为失效，不会再访问。
- **保持相对顺序**：压缩是稳定的，原本升序保持升序，`delayedEvents[0]` 仍然是最近的"下一到期时间"，`chooseDT()` 能直接用。
- **为什么不 early break**：数组近似升序，理论上看到第一个未到期就能退出。但"近似"不是严格（`pushDelayedEvent` 只插入时反向冒泡一次，多次插入后可能有轻微乱序），稳妥起见全量扫描。

## 4. `PortCreateList / PortCompletionList` 只清零不追加：完整生命周期

这两个 Component 的存在是 Phase E 的并行安全设计。我举一个完整生命周期，你就明白为什么 `deliverEvents` 只清零、谁来填、谁来消费。

### 4.1 为什么不能让 `flowArrivalOnePort` 直接创建 FlowTag？

`flowArrivalOnePort` 是按 Port 并行跑的 worker。如果它直接 `ctx.makeEntity<FlowTag>()`：

- 并行跑的多个 worker 可能同时 `makeEntity`，Madrona 分配的 Entity id 顺序**不可控**。
- 同一组输入跑两次，FlowTag 的 Entity id 可能不同 → parity 对不上。

### 4.2 Phase E 的解法：延迟创建

把"创建 Tag"拆成两步：
1. 并行阶段（`flowArrivalOnePort`）：只把"要创建什么"的元数据塞进本 Port 的 `PortCreateList`（纯 POD 写入，线程安全）。
2. 单例阶段（`flushTagCreateSystem`）：**严格按 port_id 升序**遍历 `portEntities[]`，串行调用 `createTagOnPort`。这样 Entity id 分配顺序就是确定的。

### 4.3 `PortCreateList` 一步内的生命周期

```
t=0 本步开始
  │
  ▼
deliverEvents()
  • 遍历所有 Port：PortCreateList.num = 0  ← 本函数在这清零
  • 派发 Arrival / BwUpdate / PfcControl 到 PortInbox
  │
  ▼
pfcPropagateOnePortSystem（per-Port 并行）
  • 读 PortInbox.pfcs[]，写 PortPfcState
  │
  ▼
arrivalOnePortSystem（per-Port 并行）
  • 读 PortInbox.arrivals[]
  • 对需要新建 Tag 的 flow：PortCreateList.reqs[num++] = { ... }  ← 这里追加
  │
  ▼
bwUpdateOnePortSystem（per-Port 并行）
  • 读 PortInbox.bwupds[]，更新 FlowTag.out_bw
  • 若到达终点：PortCompletionList.flow_ids[num++] = flow_id    ← 这里追加
  │
  ▼
flushTagCreateSystem（singleton，按 port_id 升序）
  • 遍历 portEntities[]，依次消费 PortCreateList.reqs[]
  • 对每条 req 调 createTagOnPort（真正创建 FlowTag Entity）
  │
  ▼
flushFlowCompletionSystem（singleton，按 port_id 升序）
  • 遍历 portEntities[]，依次消费 PortCompletionList.flow_ids[]
  • 登记 Sim::flowCompletions，清理 flowRoutes、flowDefs 等
  │
  ▼
本步结束
```

### 4.4 所以 `deliverEvents` 里 `PortCreateList/CompletionList.num = 0` 的意思是：

"本步即将开始，把上一步的 per-Port 暂存队列清空，给这一步腾地方。具体的 reqs[] / flow_ids[] 内容留着不动，反正会被新写入覆盖。"

`deliverEvents` 从不往这两个数组里追加，因为它不做任何 per-Port 业务，只做"把全局事件分到端口"。

## 5. 串起来：一个 Arrival 事件从入堆到被消费的完整路径

假设在某一步 `schedulePendingFlows` 调用了 `injectFlow(src_port_id=101, flow={id=99, ...})`。

**阶段 A：事件入堆**
```
pushDelayedEvent({ t=1.0, type=Arrival, arrival={port_id=101, flow_id=99, ...} })
  → delayedEvents[numDelayedEvents++] = ev
```

**阶段 B：deliverEvents 分发（本函数）**
```
遍历 Port：ctx.get<PortInbox>(port_101).num_arrival = 0
        ctx.get<PortCreateList>(port_101).num = 0
        ctx.get<PortCompletionList>(port_101).num = 0

扫 delayedEvents：遇到上面的 ev，t=1.0 <= now=1.0+1e-15 → 到期

  全局写：inboxArrival[numInboxArrival++] = ev
          printSystemDeliverArrival(...)
  per-Port 写：
          Entity port_e = portEntities[101];
          PortInbox &inbox = ctx.get<PortInbox>(port_e);
          inbox.arrivals[inbox.num_arrival++] = ev;
```

**阶段 C：per-Port 并行处理（不是本函数了，示意）**
```
arrivalOnePortSystem on port_101:
  for ev in inbox.arrivals[0 .. num_arrival):
    existing = findTag(port_id=101, flow_id=99)
    if existing == none:
      PortCreateList.reqs[num++] = { flow_id=99, in_bw=..., size=..., is_source=1, ... }
    else:
      update existing
```

**阶段 D：flushTagCreateSystem 串行消费**
```
for port_id = 0..numPorts-1:
  for req in PortCreateList.reqs[0 .. num):
    createTagOnPort(...)  → 创建 FlowTag Entity，挂到 PortTagList
```

**阶段 E：下一步 dt 计算**
```
chooseDT()：看 delayedEvents[0].t（压缩后最早的下一事件），决定 now 前进多少
```

**一个事件**：**1** 次入堆、**1** 次双写到 inbox、**1** 次 per-Port 消费、**1** 次 Tag 创建，全部在 1 步内完成。

## 6. 常见困惑 FAQ

**Q1：`inbox.num_arrival = 0` 是清空了数组吗？**
A：**没有**。只是把"有效长度"的游标置 0。`inbox.arrivals[0..63]` 的旧数据还在内存里。但逻辑上被视为"空"，后续 `inbox.arrivals[num_arrival++] = ev` 会从 0 开始覆盖旧数据。这是高性能写法（避免 memset）。

**Q2：为什么 `deliverEvents` 要重置 `PortInbox`，而 `PortCreateList` 也重置？后者我不是说只清零让下游填吗？**
A：两者都是 **"本步开头重置为零"** 这个动作本身一样。区别只在于：本步内 `PortInbox` 由 `deliverEvents` 自己填；`PortCreateList` 由下游 per-Port 系统填。`deliverEvents` 统一负责"开工前清场"。

**Q3：如果 `portEntities[port_id] == Entity::none()` 会怎样？**
A：说明这个 port_id 没有对应的 Port 实体（初始化没分配、或被销毁）。per-Port 写入直接跳过，但**全局 inbox 仍然写**（全局不看 Entity 是否存在）。后果是这条事件"有日志、有全局记录，但没有人会消费它"——等同丢失。

**Q4：`now + 1e-15` 这个容差为什么写这么小？**
A：典型仿真时间尺度是 us~s，1e-15 远小于任何业务 delay（最小的是 link delay 0.01us=1e-8），只用来防"浮点相等写成 `a <= a` 因累积误差变成 `a <= a - eps`"这种误判。不会误把将来事件判成现在。

**Q5：`delayedEvents` 真的永远近似升序吗？会不会压缩后第一条就不是"下一到期"？**
A：`pushDelayedEvent` 每次插入都"反向冒泡"到有序位置。压缩保持稳定（相对顺序不变）。所以**压缩后仍然近似升序**，`delayedEvents[0].t` 作为"下一到期"是可靠的。但"近似"两个字不能丢——如果某次插入时容量满被丢了事件，结果还是对的；但如果有人绕过 `pushDelayedEvent` 直接写数组，就会破坏不变量（当前代码没人这么干）。

**Q6：一个事件如果同一 port 的 `PortInbox` 满了（比如 65 个 Arrival），哪条会被丢？**
A：**第 65 条（即 `num_arrival == 64` 时再来的那条）** 被丢，已经装进去的不动。同一步内遇到的顺序决定谁留下，和事件的 `t` 无关（反正 `t` 都 `<= now`）。

**Q7：PFC 的 `source_port_id` 在 `deliverEvents` 里用到了吗？**
A：**没有**。`deliverEvents` 只拿它当"事件载荷"原样搬运。消费它的是下游 `pfcPropagateOnePort`：收到一条 PFC 后要知道"是谁告诉我的"（source）才能反向传递。

## 7. 一句话总结（深入版）

> `deliverEvents()` 的本质是 **"把一张按时间排序的全局事件数组，按目标端口分流到端口本地的 Inbox，并借机把上一步的 per-Port 暂存清空"**。它同时维护了老路径的全局 inbox（串行、有日志）和新路径的 per-Port inbox（并行、无锁），靠"双写 + 独立判容量"把两套路径粘在一起；到期判断用左右指针就地压缩，保留未到期事件的相对顺序和近似升序不变量。
