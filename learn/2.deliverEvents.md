# 2.deliverEvents：把到期的延迟事件派发到各 Port 的 Inbox

本文档聚焦 `Sim::deliverEvents(Context &ctx)`（`src/sim_systems.cpp:465`）一个函数的**业务逻辑**：它做什么、怎么做、调用了哪些子函数，最终对**全局状态**和**实体（Entity / Component）**产生了哪些修改或创建。

---

## 1. 函数在 step 流水线中的位置

`deliverEvents` 由 `deliverStepSystem` 紧接在 `schedulePendingFlows` 之后执行：

```19:23:madrona_simple_example/src/sim.cpp
void deliverStepSystem(Engine &ctx, SimDriver &)
{
    Sim &sim = ctx.data();
    sim.deliverEvents(ctx);
}
```

一步内的 ingress 链：

1. `scheduleStepSystem` → `schedulePendingFlows()`：把到时间的 FlowDef 变成 `DelayedEvent`（`t=now`）压入 `delayedEvents[]`。
2. **`deliverStepSystem` → `deliverEvents(ctx)`**：把 `delayedEvents` 里 `t <= now` 的事件**分类**派发到两处：
   - `Sim` 级全局三个 inbox（`inboxArrival / inboxBwUpdate / inboxPfc`）
   - 每个目的 `Port` 实体的 `PortInbox` 组件
3. 后续 per-Port 系统（`pfcPropagate / flowArrival / bwUpdate / ...`）读取自己的 `PortInbox` 完成真正的业务。

所以 `deliverEvents` 是**事件系统的「出口路由器」**：从单一优先级队列 `delayedEvents` 分发到按端口并行可消费的 inbox。

## 2. 函数主逻辑（逐段拆解）

### 2.1 日志前置与全局 inbox 清空

```467:478:madrona_simple_example/src/sim_systems.cpp
constexpr const char *scope = "ingress_chain";
uint64_t step = systemLogStep;
bool log_enabled = systemLogEnabled(scope, step);
int32_t delayed_before = numDelayedEvents;

if (log_enabled) {
    printSystemBegin(step, now, scope, "deliver_events");
}

numInboxArrival = 0;
numInboxBwUpdate = 0;
numInboxPfc = 0;
```

- 取 `scope / step / log_enabled / delayed_before` 用于日志统计。
- **清零**三个全局 inbox 计数：`numInboxArrival / numInboxBwUpdate / numInboxPfc`。底层数组内容不擦除，只复位游标（后续会被覆盖写入）。

### 2.2 每个 Port 的组件重置

```480:493:madrona_simple_example/src/sim_systems.cpp
// Phase E: also reset every Port's PortInbox / PortCreateList /
// PortCompletionList before dispatching this frame's due events.
for (int32_t port_id = 0; port_id < numPorts; port_id++) {
    Entity port_e = portEntities[port_id];
    if (port_e == Entity::none()) {
        continue;
    }
    PortInbox &inbox = ctx.get<PortInbox>(port_e);
    inbox.num_arrival = 0;
    inbox.num_bwupd = 0;
    inbox.num_pfc = 0;
    ctx.get<PortCreateList>(port_e).num = 0;
    ctx.get<PortCompletionList>(port_e).num = 0;
}
```

为什么在这里重置？—— Phase E 的约定是：每一步开始派发事件前，必须把上一步遗留的 per-Port 暂存全部清空，避免 per-Port 并行系统重复消费。

具体清空 3 个 Component（仅改计数，数组内容保留）：

| Component | 字段 | 作用 |
|---|---|---|
| `PortInbox` | `num_arrival / num_bwupd / num_pfc` | 本步要接收的三类事件数量 |
| `PortCreateList` | `num` | Phase E 延迟创建 Tag 的请求队列（下游 flowArrival 产生，flushTagCreateSystem 消费） |
| `PortCompletionList` | `num` | Phase E 延迟的流完成登记（下游 bwUpdate 产生，flushFlowCompletion 消费） |

> 重要：`deliverEvents` 只做**清零**，后续 per-Port 系统才会**写入** `PortCreateList / PortCompletionList`。所以这两个清零是为下游系统让路，**不是**给本函数自己填的。

### 2.3 主循环：扫描 `delayedEvents`，到期的分发、未到期的原地保留

```495:554:madrona_simple_example/src/sim_systems.cpp
int32_t write_idx = 0;
for (int32_t i = 0; i < numDelayedEvents; i++) {
    if (delayedEvents[i].t <= now + 1e-15) {
        // 按类型分发到 全局inbox + 目标Port的PortInbox
        ...
    } else {
        delayedEvents[write_idx++] = delayedEvents[i];
    }
}
numDelayedEvents = write_idx;
```

采用**双指针压缩**：
- `i` 顺序扫描所有事件；
- `write_idx` 只前移那些**还没到期**的事件；
- 结束时 `numDelayedEvents = write_idx`，等价于“把到期事件移出队列，未到期的保持原相对顺序”。
- 1e-15 的浮点容差保证 `t == now` 也被判定到期。

由于 `pushDelayedEvent` 维护了 `delayedEvents[]` 按 `t` 近似有序，这里也可以用“早停”，但当前实现是**全量扫描**（安全且简单）。

#### 2.3.1 Arrival 分支（`DelayedEvent::Type::Arrival`）

```498:514:madrona_simple_example/src/sim_systems.cpp
if (delayedEvents[i].type == DelayedEvent::Type::Arrival) {
    const FlowArrivalEv &ev = delayedEvents[i].arrival;
    if (numInboxArrival < MAX_EVENTS_PER_STEP) {
        inboxArrival[numInboxArrival++] = ev;
        if (log_enabled) { printSystemDeliverArrival(step, now, ev); }
    }
    if (ev.port_id >= 0 && ev.port_id < numPorts) {
        Entity port_e = portEntities[ev.port_id];
        if (port_e != Entity::none()) {
            PortInbox &inbox = ctx.get<PortInbox>(port_e);
            if (inbox.num_arrival < MAX_PORT_INBOX_ARRIVAL) {
                inbox.arrivals[inbox.num_arrival++] = ev;
            }
        }
    }
}
```

两处写入**相互独立**：
- **全局层**：`inboxArrival[numInboxArrival++] = ev`（容量 `MAX_EVENTS_PER_STEP = 16384`）。
- **端口层**：依据 `ev.port_id` 找 `portEntities[port_id]`，写到该 Port 的 `PortInbox.arrivals[]`（容量 `MAX_PORT_INBOX_ARRIVAL = 64`）。
- 任一方向写满都**静默丢弃**该事件的对应副本（不回退事件，不报错）。
- 日志 `printSystemDeliverArrival` 只在全局层写入成功时才打印。

#### 2.3.2 BwUpdate 分支（`DelayedEvent::Type::BwUpdate`）

```515:531:madrona_simple_example/src/sim_systems.cpp
} else if (delayedEvents[i].type == DelayedEvent::Type::BwUpdate) {
    const BwUpdateEv &ev = delayedEvents[i].bwupd;
    ...

```

结构与 Arrival 完全对称：
- 全局层写 `inboxBwUpdate[numInboxBwUpdate++]`；
- 端口层用 `ev.port_id` 定位 Port，写 `PortInbox.bwupds[]`（容量 `MAX_PORT_INBOX_BWUPD = 64`）；
- 日志 `printSystemDeliverBwUpdate`。

#### 2.3.3 PfcControl 分支（`DelayedEvent::Type::PfcControl`）

```532:548:madrona_simple_example/src/sim_systems.cpp
} else {
    const PfcControlEv &ev = delayedEvents[i].pfcctrl;

    if (ev.target_port_id >= 0 && ev.target_port_id < numPorts) {
```

- 全局层写 `inboxPfc[numInboxPfc++]`；
- 端口层写 `PortInbox.pfcs[]`（容量 `MAX_PORT_INBOX_PFC = 32`）；

## 3. 子函数 / 外部依赖

`deliverEvents` 并未调用任何 `Sim::xxx` 业务子函数（不像 `schedulePendingFlows` 要穿 `injectFlow / pushDelayedEvent`）。它只调用：

| 外部调用 | 作用 | 是否改状态 |
|---|---|---|
| `systemLogEnabled(scope, step)` | 判断是否需要打印日志 | 否（只读） |
| `printSystemBegin / End / DeliverArrival / DeliverBwUpdate / DeliverPfc / DeliverSummary` | 结构化日志输出 | 否（仅 I/O） |
| `ctx.get<PortInbox>(port_e)` / `ctx.get<PortCreateList>(port_e)` / `ctx.get<PortCompletionList>(port_e)` | Madrona ECS 组件取引用 | **是**，后续通过引用写组件字段 |

换句话说，**所有业务副作用都集中在本函数体内直接展开**，没有下沉到其他辅助函数。

## 4. 总结：对实体 / 全局状态产生的修改

### 4.1 全局状态（`Sim` 成员）修改

| 状态 | 变化 | 说明 |
|---|---|---|
| `numInboxArrival` + `inboxArrival[]` | **清零后重填** | 本步所有到期 Arrival（含所有 Port 的），容量上限 `MAX_EVENTS_PER_STEP=16384`，溢出静默丢 |
| `numInboxBwUpdate` + `inboxBwUpdate[]` | **清零后重填** | 同上，BwUpdate |
| `numInboxPfc` + `inboxPfc[]` | **清零后重填** | 同上，PfcControl |
| `delayedEvents[]` + `numDelayedEvents` | **压缩** | 到期事件被剔除；未到期事件按原相对顺序保留；数组尾部残留内容不清零 |
| `now / numPorts / portEntities / systemLogStep` | 只读 | 仅用于定位端口 / 打日志 |

### 4.2 ECS 实体 / Component 修改

**不创建**任何实体。对每一个合法 `Port` 实体（`portEntities[port_id] != Entity::none()`）修改以下 3 个 Component：

| Archetype | Component | 字段变化 | 语义 |
|---|---|---|---|
| `Port` | `PortInbox` | `num_arrival / num_bwupd / num_pfc` 先清零；随后按事件追加到 `arrivals[] / bwupds[] / pfcs[]` | 本步该端口要消费的到期事件；单 Port 容量 64/64/32，溢出静默丢 |
| `Port` | `PortCreateList` | `num = 0`（**只清零**，本函数不写 `reqs[]`） | 为下游 `flowArrivalOnePort` 暂存延迟 Tag 创建请求让路 |
| `Port` | `PortCompletionList` | `num = 0`（**只清零**，本函数不写 `flow_ids[]`） | 为下游 `bwUpdateOnePort` 暂存流完成登记让路 |

> 特别注意：
> - `PortCreateList` 和 `PortCompletionList` 在本函数里**只清零、不追加**，清零是“每步预算重置”。真正写入它们的是后续 per-Port 系统（`flowArrivalOnePort` / `bwUpdateOnePort`），消费它们的是 `flushTagCreateSystem` / `flushFlowCompletionSystem`。
> - `PortInbox` 在本函数内**先清零、后追加**，和全局 inbox 双路并写。

### 4.3 事件路由的两个关键点

1. **同一事件会被写两份**：一份进全局 `inboxXxx[]`，一份进目标 Port 的 `PortInbox`。两者独立判容量，任何一边满了都只影响对应那一份；**不会回退事件**。
2. **Arrival / BwUpdate 用 `ev.port_id` 路由；PfcControl 用 `ev.target_port_id` 路由**。这是唯一一处方向语义差异，源于 PFC 是"反向"通知上游端口暂停发送。

### 4.4 边界与失败行为

- `portEntities[port_id] == Entity::none()`：跳过端口侧写入，只写全局 inbox（若仍有容量）。
- `ev.port_id / target_port_id` 越界（<0 或 >= numPorts）：跳过端口侧写入。
- 全局 inbox 已满：跳过全局侧写入并**不打印该事件日志**。
- 端口 inbox 已满：跳过端口侧写入（事件可能只在全局层可见，但 per-Port 系统看不到）。
- 未到期事件：通过 `delayedEvents[write_idx++]` 原地压缩保留，等待下一步重试。

---

## 5. 一句话概括

> `deliverEvents()` 在一步开始时**先把所有 Port 的 `PortInbox / PortCreateList / PortCompletionList` 计数清零**，然后扫描 `delayedEvents[]`，将 `t <= now` 的事件按类型（Arrival / BwUpdate / PfcControl）**同时写入全局 `inboxXxx[]` 和目标 Port 的 `PortInbox`**，未到期事件原地压缩保留；不创建任何实体，也不触碰 Tag / PortBuffer 等业务状态，真正的流级处理在下游 per-Port 系统里进行。
