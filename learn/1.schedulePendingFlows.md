# 1.schedulePendingFlows：挂起流的调度入口

本文档聚焦 `Sim::schedulePendingFlows()`（`src/sim_systems.cpp:411`）这一个函数的**业务逻辑**：它做什么、怎么做、调用了哪些子函数，最终对**全局状态**和**实体（Entity / Component）**产生了哪些修改或创建。

---

## 1. 函数在整个 step 流水线中的位置

`schedulePendingFlows()` 由 `scheduleStepSystem` 在每一步开始时调用（`src/sim.cpp:16`）：

```11:17:madrona_simple_example/src/sim.cpp
void scheduleStepSystem(Engine &ctx, SimDriver &driver)
{
    Sim &sim = ctx.data();
    sim.systemLogStep += 1;
    driver.tick += 1;
    sim.schedulePendingFlows();
}
```

一步的调度链大致是：

1. `scheduleStepSystem` → `schedulePendingFlows()` —— 把“到时间”的流从待排队列（`pendingFlows`）取出来，注入到延迟事件队列（`delayedEvents`）。
2. `deliverStepSystem` → `deliverEvents(ctx)` —— 从 `delayedEvents` 把到期事件派发到各 Port 的 Inbox。
3. 后续的 per-Port ingress 系统（`pfcPropagate / flowArrival / bwUpdate / ...`）再消费 Inbox。

所以 `schedulePendingFlows` 扮演的角色是**仿真的「时间门」**：只让 `start_time <= now` 的流进入事件管线，其余的仍然留在 `pendingFlows` 里等下一步。

## 2. 函数主逻辑（逐行拆解）

```411:463:madrona_simple_example/src/sim_systems.cpp
void Sim::schedulePendingFlows()
{
    constexpr const char *scope = "ingress_chain";
    uint64_t step = systemLogStep;
    bool log_enabled = systemLogEnabled(scope, step);
    int32_t pending_before = numPendingFlows;
    int32_t delayed_before = numDelayedEvents;
    int32_t flow_routes_before = numFlowRoutes;
    int32_t scheduled_count = 0;
    FlowDef logged_flows[MAX_FLOWS] {};
    int32_t num_logged_flows = 0;
    ...
}
```

### 2.1 准备与日志前置
- 记录 `scope = "ingress_chain"`、当前 `step = systemLogStep`。
- 读取三个“before”快照：`numPendingFlows`、`numDelayedEvents`、`numFlowRoutes`，用于最后打日志做差值。
- 局部数组 `logged_flows[MAX_FLOWS]` 只用来收集本步被调度的 `FlowDef`，最后按 `id` 排序后打印（仅日志用途，不影响仿真状态）。
- `if (log_enabled)` 时调用 `printSystemBegin` 标记“开始”。

### 2.2 核心循环：从 `pendingFlows` 提取到期流

```427:438:madrona_simple_example/src/sim_systems.cpp
while (numPendingFlows > 0 && pendingFlows[0].start_time <= now + 1e-15) {
    FlowDef flow = pendingFlows[0];
    for (int32_t i = 1; i < numPendingFlows; i++) {
        pendingFlows[i - 1] = pendingFlows[i];
    }
    numPendingFlows -= 1;
    if (log_enabled && num_logged_flows < MAX_FLOWS) {
        logged_flows[num_logged_flows++] = flow;
    }
    scheduled_count += 1;
    injectFlowDef(flow);
}
```

关键点：

1. **触发条件**：只有当队首 `pendingFlows[0].start_time <= now + 1e-15` 时才弹出（加 `1e-15` 是浮点容差）。这说明 `pendingFlows` 是按 `start_time` 升序维护的——在 `init` 阶段就已经排好。
2. **弹出方式**：整体左移一格（`O(n)`），`numPendingFlows -= 1`。这是一个“软队列”的实现，没有用环形缓冲。
3. **循环不变式**：只要队首还到期，就继续弹。所以一步里可以把**所有** `start_time <= now` 的流全部调度掉，而不是只调度一个。
4. **日志**：把 flow 记进 `logged_flows` 以便最后排序打印；真正业务动作在 `injectFlowDef(flow)`。

## 3. 调用链：子函数做了什么

`schedulePendingFlows` 自身只做“取流 + 打日志”，真正修改全局/实体的动作下沉到这条链：

```
schedulePendingFlows
  └── injectFlowDef(flow)                    // sim_systems.cpp:353
        ├── getPath(src, dst, flow_id, ...)  // sim_world.cpp:144   计算 node 路径
        ├── findNodeSlot / findNeighborSlot  // sim_world.cpp:27/38 查拓扑槽位
        ├── [追加] flowRoutes[numFlowRoutes++] = route   // 路由缓存
        └── injectFlow(src_port_id, flow)    // sim_systems.cpp:320
              └── pushDelayedEvent(ev)       // sim_world.cpp:228  入事件堆
```

### 3.1 `injectFlowDef(const FlowDef &flow)` (sim_systems.cpp:353)

职责：**把一条业务级 `FlowDef` 落成“路由 + 到达事件”**。步骤：

1. 调 `getPath(flow.src_node, flow.dst_node, flow.id, path, MAX_PATH_NODES)`，在拓扑上算出一条 NodeId 序列 `path`。
   - 对 `Host`：若能直达 dst 就直接到；否则走第一个 neighbor（通常是上行 ToR）。
   - 对 `Switch`：优先用 ECMP 候选（按 `flow_id` 哈希选一个），否则回退到 `routeTable` 的下一跳。
   - 路径太长（>=`MAX_PATH_NODES`）或断链时返回 0，`injectFlowDef` 直接 `return`，**不产生任何修改**。
2. `path_len < 2` 则 `return`（没有真实跳数）。
3. 用 `findNodeSlot / findNeighborSlot` 沿 `path` 解析每一跳的 `port_id`，拼出 `port_path[]`。末尾补一个 `-1` 作为“最后一跳无下一跳”的哨兵。
4. 线性扫描 `flowRoutes[0..numFlowRoutes)`，若 `flow_id` 已存在就**跳过**路由写入（幂等）；否则当 `numFlowRoutes < MAX_FLOWS` 时**新增一条 `FlowRouteState`**：
   - `route.flow_id = flow.id`
   - `route.num_steps = port_path_len - 1`
   - `route.steps[i] = { port_id, next_port_id }`
   > 注意：这是写在 `Sim` 的全局数组 `flowRoutes[]` 里，不是创建 ECS Entity。
5. 取源节点在源端口方向的 `src_port_id`，调用 `injectFlow(src_port_id, flow)`。

### 3.2 `injectFlow(int32_t src_port_id, const FlowDef &flow)` (sim_systems.cpp:320)

职责：**构造一个 Arrival 延迟事件并入堆**。

1. 算出源端口的输入带宽 `src_in_bw`：
   - 找到 `src_port_id` 对应的 `TopoNodeState` 及邻居；
   - 若 `topoLinks[src_port_id].bandwidth > 0` 用 link 带宽，否则退回到 `node.port_bw`。
2. 构造 `DelayedEvent`：
   - `ev.t = now`（注意：**立刻派发**，不加额外延迟，因为到期判断已经在 `schedulePendingFlows` 做完了）。
   - `ev.type = Arrival`。
   - `ev.arrival = FlowArrivalEv { port_id, flow_id, size, in_bw, is_source=1, priority }`。
3. `pushDelayedEvent(ev)`。

### 3.3 `pushDelayedEvent(const DelayedEvent &ev)` (sim_world.cpp:228)

职责：把事件按 `t` 升序插入 `delayedEvents[]`。

- 若 `numDelayedEvents >= MAX_DELAYED_EVENTS`，**丢弃**（静默失败）。
- 否则尾插 + 一次“反向冒泡”（把新元素往前挪到合适位置），保持数组对 `t` 近似有序。

### 3.4 `getPath / findNodeSlot / findNeighborSlot`

纯只读查询函数，不修改任何状态：
- `findNodeSlot(NodeId)`：线性找 `topoNodes[]` 里匹配的 slot。
- `findNeighborSlot(slot, neighbor_id)`：在该 node 的 neighbors 里线性找。
- `getPath`：根据 `routeTable / ecmpNextHops / ecmpCount` 按 `flow_id` 选 ECMP 下一跳，沿 host/switch 规则把 NodeId 序列写入 `out_path`，返回长度。

## 4. 总结：对实体 / 全局状态产生的修改

`schedulePendingFlows` 自身**不直接**接触任何 ECS `ctx.get<>`，它的所有副作用都通过 `injectFlowDef` → `injectFlow` → `pushDelayedEvent` 落到 `Sim` 的全局数组上。它**不创建任何 ECS Entity**，也不修改 Port/Tag 等 Component。真正的 Entity 创建发生在下游的 `flowArrivalSystem`（由后续的 `deliverEvents` + per-Port Ingress 处理）。

### 4.1 全局状态（Sim 成员）修改

| 状态 | 变化 | 说明 |
|---|---|---|
| `pendingFlows[]` + `numPendingFlows` | **移除**（左移收缩） | 每弹出一条到期流就 -1；对象内容不复用 |
| `flowRoutes[]` + `numFlowRoutes` | **新增**（幂等） | 首次见到 `flow_id` 时追加 1 条 `FlowRouteState`，已存在则跳过；容量上限 `MAX_FLOWS` |
| `delayedEvents[]` + `numDelayedEvents` | **新增** | 每条被成功注入的 flow 增加 1 个 `Arrival` 类型 `DelayedEvent`（`t=now`），按 `t` 插入保持近似有序；超过 `MAX_DELAYED_EVENTS` 会静默丢弃 |
| `systemLogStep` | **不改** | 自增在上层 `scheduleStepSystem` 里完成 |
| `now` / `numPorts` / `topoNodes` / `topoLinks` / `portToNode` / `routeTable` / `ecmpNextHops` | 只读 | 仅用于路径计算 |

### 4.2 实体 / Component 修改

- **创建的实体**：无。
- **修改的 Component**：无。
- `schedulePendingFlows` 执行完后，`DirtyPort`、`PortInbox`、`FlowTagState` 等全部保持不变；这些要等到下游 `deliverEvents` 把 `DelayedEvent` 派发到 `PortInbox`、再由 `flowArrivalSystem / flowArrivalOnePort` 调 `createTagOnPort` 时才真正改动。

### 4.3 典型的失败/边界情况

- `getPath` 返回 `<2`：整个 `injectFlowDef` 直接返回 —— **flow 被从 `pendingFlows` 移除但没产生路由和到达事件**（等价于“丢弃”）。
- `numFlowRoutes == MAX_FLOWS`：路由不再新增，但仍然会调用 `injectFlow`（事件照样入堆）。
- `numDelayedEvents == MAX_DELAYED_EVENTS`：事件被静默丢弃；`pendingFlows` 里的 flow 已经出队，事实上**也会被丢**。
- `start_time > now`：不做任何事，循环立即退出，所有 flow 留在 `pendingFlows` 里等下一步。

---

## 5. 一句话概括

> `schedulePendingFlows()` 把**所有 `start_time <= now` 的 `FlowDef`** 从 `pendingFlows` 弹出，为每条流**在 `flowRoutes` 里登记一条端口级路由（幂等）**并**向 `delayedEvents` 推入一个 `t=now` 的 `Arrival` 事件**；不创建也不修改任何 ECS 实体，所有 Entity 级别的动作由后续 `deliverEvents` + `flowArrivalSystem` 完成。
